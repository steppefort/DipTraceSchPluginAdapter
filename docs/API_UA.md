# API 1: інтерфейс плагіна та життєвий цикл

[English](API.md) · Українська · [README](../README_UA.md)

Цей документ описує, як DipTraceSchPluginAdapter запускає плагін, передає йому вхідні дані та повертає зміни в DipTrace. Інструкцію встановлення та покроковий приклад створення плагіна наведено в [README](../README_UA.md).

## Запуск і виконання

DipTrace запускає EXE плагіна з одним позиційним аргументом — шляхом до тимчасового XML-файлу обміну. EXE знаходить `adapter.ini` та `.adapter/host.py` поруч із собою, незалежно від робочого каталогу DipTrace.

Послідовність запуску:

1. EXE запускає Python-процес керування без вікна консолі. Python успадковує середовище процесу запуску.
2. Процес керування перевіряє налаштування та вхідний XML, створює каталог запуску й зберігає копію XML як `exchange.xml`.
3. Процес керування записує `context.json` і запускає окремий робочий процес Python, який викликає `main(ctx)` із вхідного файлу плагіна.
4. У режимі `job` процес керування завершується після запуску робочого процесу. EXE також завершується, а DipTrace продовжує роботу. Робочий процес виконує завдання незалежно.
5. У режимі `ui` процес керування очікує завершення робочого процесу. Якщо той завершився успішно й підготував результат, процес керування перевіряє його та записує до початкового файлу обміну до завершення EXE.

| Режим | Обов’язкові параметри обміну в `settings.xml` | Повернення змін у схему |
| --- | --- | --- |
| `job` | `ImpMode=None` | Заборонено. |
| `ui` | `ExpMode=All` та `ImpMode=All` | Через `ctx.commit_xml()`. |

Режим визначає порядок виконання та імпорту, а не бібліотеку інтерфейсу. Плагін може використовувати Tkinter, Qt або іншу бібліотеку. Цикл подій вікна має працювати всередині `main()`. Усі дії, що впливають на повернений XML, потрібно завершити до повернення з `main()`.

DipTrace імпортує зміни після завершення EXE плагіна. Контекст належить одному запуску й не надає постійного з’єднання з активним проєктом.

## Точка входу плагіна

Файл, указаний у параметрі `[plugin] entry` файлу `adapter.ini`, має визначати функцію:

```python
def main(ctx):
    document = ctx.document()
    variables = ctx.environment(["author", "Company"])
    ctx.log("Плагін запущено")
    # Реалізуйте функціональність плагіна тут.
```

Адаптер передає `ctx` автоматично. У разі успіху поверніть `None` або `0`. Виняток чи ненульовий результат позначає запуск як невдалий і відкидає підготовлений XML.

Для редактора викличте `ctx.commit_xml(document)` після підтвердження змін користувачем, а потім дайте `main()` завершитися. Цей виклик готує результат, але не оновлює схему негайно. Виклик `ctx.cancel()` відкидає підготовлений результат. Повернення без підготовленого результату також залишає схему без змін.

Ці правила стосуються XML, який повертається в DipTrace. Файли, створені або змінені безпосередньо кодом плагіна, автоматично не відкочуються.

## API контексту

| Метод або властивість | Опис |
| --- | --- |
| `ctx.exchange_path` | Шлях до збереженого `exchange.xml`. Цей файл не можна змінювати. |
| `ctx.read_xml()` | Повертає початкові байти XML після перевірки їхнього хешу SHA-256. |
| `ctx.document()` | Повертає новий кореневий елемент `xml.etree.ElementTree.Element`, прочитаний із копії XML, зі збереженням коментарів, інструкцій обробки та невідомих вузлів. |
| `ctx.project_dir` | `pathlib.Path` із `/Source/Schematic/Settings/ProjectDir` або `None`, якщо значення відсутнє чи порожнє. Відносний шлях відраховується від каталогу плагіна. |
| `ctx.plugin_dir` | Каталог плагіна як `pathlib.Path`. |
| `ctx.run_dir` | Каталог поточного запуску як `pathlib.Path`. |
| `ctx.plugin_id`, `ctx.mode` | Ідентифікатор і режим цього запуску. |
| `ctx.adapter_version` | Версія адаптера, що створив контекст. |
| `ctx.plugin_version` | Версія плагіна з `[plugin] version`, або `None`, якщо її не задано. |
| `ctx.environment(names)` | Повертає запитані успадковані змінні середовища з нормалізованими ключами. Див. [Змінні середовища](#змінні-середовища). |
| `ctx.commit_xml(bytes_or_root)` | Готує повний XML-документ, переданий як `bytes` або кореневий `Element`. Доступний лише в режимі `ui`. |
| `ctx.cancel()` | Відкидає підготовлений результат і позначає запуск як скасований. Подальші виклики `commit_xml()` відхиляються. |
| `ctx.log(message)` | Додає повідомлення до `plugin.log`. |

Використовуйте контекст лише для поточного запуску. Не застосовуйте його повторно після відкриття іншого проєкту. Код плагіна читає збережену копію; шлях до початкового тимчасового файлу DipTrace йому не потрібен.

## Файл запиту

`context.json` — JSON-файл у кодуванні UTF-8, розташований у каталозі запуску. Поля API 1:

| Ключ | Опис |
| --- | --- |
| `api_version` | Ціле число `1`. Несумісні версії відхиляються. |
| `mode` | `job` або `ui`. |
| `plugin_id` | ASCII-ідентифікатор плагіна, який використовується для діагностики. |
| `plugin_dir` | Абсолютний шлях до каталогу плагіна. |
| `entry` | Абсолютний шлях до Python-файлу з точкою входу плагіна. |
| `config_path` | Абсолютний шлях до `adapter.ini`. |
| `source_sha256` | Хеш SHA-256 файлу `exchange.xml` цього запуску. |
| `write_scope` | `sheet_settings` або `full`. |
| `settings` | Об’єкт із `ExpMode` та `ImpMode`, перевіреними під час запуску. |

Робочий процес завжди читає `exchange.xml` поруч із `context.json`. Збережена копія має залишатися незмінною протягом усього запуску.

## Результат та імпорт

`status.json` містить `api_version` і `status`. Для успішних і скасованих запусків файл також містить `result_sha256` — хеш підготовленого результату або `null`. У разі помилки додається поле `error` із трасуванням винятку.

| Стан | Значення |
| --- | --- |
| `starting` | Запуск ініціалізовано; робочий процес ще не записав остаточний стан. |
| `ok` | `main()` успішно завершилася без підготовленого XML. |
| `changed` | `main()` успішно завершилася з підготовленим `result.xml` та його `result_sha256`. |
| `cancelled` | Плагін явно скасував запуск. |
| `error` | Виконання завершилося помилкою; результат для імпорту відсутній. |

Процес керування приймає `changed` лише в режимі `ui`. Перед поверненням результату він:

1. Перевіряє, що збережена копія XML і початковий файл обміну досі відповідають `source_sha256`.
2. Перевіряє `result.xml` за `result_sha256`.
3. Перевіряє тип XML-документа та дозволену область змін.
4. Атомарно замінює початковий файл обміну, якщо результат відрізняється від вхідних даних, і фіксує запис у `applied.json`.

`changed` означає, що результат підготовлено, а не що DipTrace вже імпортував його. `applied.json` підтверджує запис у файл обміну; DipTrace виконує імпорт після завершення EXE. Якщо результат побайтово ідентичний вхідним даним, процес керування не перезаписує файл і не створює `applied.json`.

У режимі `job` успішне завершення EXE підтверджує запуск робочого процесу. Завершення самого завдання перевіряйте за `status.json`. Під час запуску залежності не завантажуються й пакети не встановлюються.

## Область змін XML

Параметр `[adapter] write_scope` визначає, які частини XML можна змінювати:

| Значення | Дозволені зміни |
| --- | --- |
| `sheet_settings` | Лише всередині `/Source/Schematic/SheetSettings`. Значення за замовчуванням. |
| `full` | Зміни в усьому XML схеми, включно з редагуванням і видаленням. Атрибути кореневого `Source` мають залишатися незмінними. |

У режимі `sheet_settings` адаптер структурно порівнює все поза `SheetSettings`, включно з невідомими вузлами й атрибутами. Пробільні символи, які слугують відступами між елементами, ігноруються; текст кінцевих елементів залишається значущим.

В обох режимах повертайте повний XML-документ. API 1 не підтримує повернення окремих змін для конкретних об’єктів. Налаштування експорту та імпорту в `settings.xml` мають відповідати вибраному режиму й поведінці плагіна.

Адаптер відхиляє оголошення DTD та сутностей. Він перевіряє структуру документа й дозволену область змін, але не виконує повну перевірку за XML-схемою DipTrace.

## Змінні середовища

`ctx.environment(["author", "Company"])` читає вибрані значення із середовища, успадкованого Python-процесом. Метод не читає постійні системні налаштування Windows і не створює та не редагує змінні в **Tools > Environment variables** DipTrace.

З імен видаляються крайні пробільні символи; дозволено необов’язкові обгортки `<...>` або `%...%`. Імена нормалізуються через `str.casefold()`. Ключі поверненого словника мають нормалізовану форму: запитуйте `Company`, а читайте `values["company"]`.

Відсутні змінні не додаються до словника; наявні змінні з порожнім значенням у ньому залишаються. Якщо кілька успадкованих імен нормалізуються до одного ключа, але мають різні значення, метод повідомляє про помилку.

До `selected_environment.json` записуються лише запитані змінні, які вдалося знайти. Повторні виклики накопичують ці вибрані значення для поточного запуску. Знімок призначений для перегляду; під час ручного повторного запуску його значення автоматично не завантажуються в середовище процесу.

## Сумісність версій

Версія API відокремлена від версії випуску адаптера. Закріплюйте повний комплект адаптера за конкретним комітом репозиторію, включно з EXE та службовими Python-модулями. Несумісні зміни формату запиту або контракту точки входу плагіна потребують нової версії API.

Використовуйте [`tools/vendor_adapter.py`](../tools/vendor_adapter.py) для встановлення чи оновлення узгоджених файлів і зберігайте `adapter.lock.json`. Не поєднуйте EXE однієї версії адаптера зі службовими модулями іншої, неузгодженої версії. Див. [налаштування залежності в README](../README_UA.md#залежність-від-репозиторію-адаптера).

## Метадані версії

`diptrace_adapter.__version__` та `diptrace_adapter.API_VERSION` читаються зі
згенерованої копії `build_info.json`. Команда `py -3 .adapter/host.py --version`
показує версію встановленої Python-частини без запуску плагіна.
Версії плагіна та адаптера незалежні; оновлення залежності не змінює назву
плагіна в меню DipTrace.
