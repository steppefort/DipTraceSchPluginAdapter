# Перенесення наявного плагіна на DipTraceSchPluginAdapter

[English](MIGRATION.md) · Українська · [README](../README_UA.md) · [API](API_UA.md)

Ця інструкція описує заміну засобу запуску та коду обміну XML наявного плагіна на DipTraceSchPluginAdapter. Плагін зберігає власну прикладну логіку, інтерфейс, налаштування й шаблони. BOMJob і TitleJob ілюструють два підтримувані режими.

## Розподіл файлів

| Репозиторій адаптера | Пакет окремого плагіна |
| --- | --- |
| Вихідний код засобу запуску та готовий EXE | Копія EXE, перейменована для плагіна |
| Вихідний код Python API та службових модулів | Службові модулі в `.adapter` |
| Інструменти створення плагінів і підключення залежності, тести, CI та документація | `plugin.py`, прикладні модулі, налаштування, шаблони та інші ресурси |

Закріпіть адаптер за конкретним комітом репозиторію. Під час підготовки випуску плагіна використовуйте `tools/vendor_adapter.py`, щоб отримати узгоджені EXE та службові модулі. Користувачам готового пакета не потрібні Git або компілятор, але потрібні Python і пакети, від яких залежить плагін.

Для переходу на новішу версію адаптера оновіть закріплений коміт і підготуйте новий пакет плагіна. Під час запуску з DipTrace плагін не виконує `git pull` і не завантажує оновлення. Див. [налаштування залежності](../README_UA.md#залежність-від-репозиторію-адаптера).

## Загальний порядок перенесення

1. Створіть нову папку плагіна через `tools/new_plugin.py`. Оберіть `job` для фонових завдань, які створюють файли, або `ui` для редактора, який повертає зміни в схему.
2. Скопіюйте прикладні модулі, налаштування й ресурси наявного плагіна до нової папки. Збережіть створені генератором EXE, `.adapter`, `adapter.ini` та `settings.xml`.
3. Реалізуйте `main(ctx)` у `plugin.py`. Читайте збережені вхідні дані через `ctx.read_xml()` або `ctx.document()` та використовуйте шляхи з контексту для ресурсів і результатів.
4. Для редактора підготуйте повний змінений документ через `ctx.commit_xml()` після підтвердження користувачем. Завершіть цикл подій і поверніться з `main()`, щоб адаптер міг передати результат у DipTrace.
5. Перевірте новий плагін у DipTrace перед заміною наявного встановлення. Перевірте як успішне виконання, так і скасування або помилку.

Не копіюйте старий EXE засобу запуску чи його стартові скрипти до нового пакета. У папці плагіна має бути один EXE, а значення `ExeFile` у `settings.xml` має відповідати його імені.

## BOMJob 0.2.7: фонове завдання

BOMJob створює ODS-файл без повернення змін у схему, тому використовує режим `job`.

### 1. Створіть окрему папку плагіна

З кореня репозиторію адаптера в PowerShell:

```powershell
py -3 tools/new_plugin.py D:\PluginBuild\BOMJobNext --name BOMJobNext --mode job
```

Каталог призначення ще не повинен існувати. Команда створює повну основу плагіна з перейменованим адаптером і демонстраційним `plugin.py`.

### 2. Скопіюйте прикладні файли BOMJob

Скопіюйте з робочого встановлення BOMJob 0.2.7 до `D:\PluginBuild\BOMJobNext`:

- `bomjob.py`, `bom_core.py`, `bom_output.py` та `bom_page_labels.py`.
- `diptrace_environment.py` та `inspect_xml.py`.
- `bomjob.ini` та каталог `templates`, включно із шаблонами, указаними в налаштуваннях.

Збережіть також додаткові ресурси, на які посилаються ваші налаштування. Перевірте шляхи, що вказують на попередній каталог встановлення.

### 3. Замініть демонстраційну точку входу

Скопіюйте [`examples/bomjob_bridge/plugin.py`](../examples/bomjob_bridge/plugin.py) до `D:\PluginBuild\BOMJobNext\plugin.py`, замінивши створений генератором приклад. Цей модуль викликає наявний обробник BOMJob зі збереженим XML, файлом `bomjob.ini` плагіна та параметром `--pause never`.

`adapter.ini` налаштовує спільний засіб запуску та службові модулі. `bomjob.ini` надалі налаштовує формування BOM. Старий засіб запуску та його стартові налаштування адаптер не використовує.

### 4. Перевірте налаштування й результат

Залиште `mode=job` у `adapter.ini`, а також `ExpMode=All` і `ImpMode=None` у `settings.xml`. Налаштуйте виконуваний файл Python за інструкцією в [README](../README_UA.md).

Установіть усю нову папку в DipTrace й запустіть плагін на тестовому проєкті. Перевірте створений ODS, шлях виведення з налаштувань BOM та остаточний `status.json` робочого процесу. Переконайтеся, що схема не змінилася. Успішне завершення EXE в режимі `job` підтверджує запуск робочого процесу, а не завершення формування BOM.

## TitleJob: редактор із Apply та Cancel

TitleJob використовує режим `ui`, оскільки повертає зміни в поля рамок. Інтерфейс, робота з VPT і правила замін залишаються частиною TitleJob; спільний адаптер забезпечує запуск і обмін XML.

Створіть окрему основу плагіна з кореня репозиторію адаптера:

```powershell
py -3 tools/new_plugin.py D:\PluginBuild\TitleJobNext --name TitleJobNext --mode ui
```

Скопіюйте прикладні модулі й ресурси наявного TitleJob, потім адаптуйте наведені нижче точки взаємодії.

| Точка взаємодії | API або налаштування адаптера |
| --- | --- |
| Точка входу | `main(ctx)` |
| Вхідний XML | `ctx.read_xml()` або `ctx.document()` |
| Запитувані змінні середовища | `ctx.environment(["author", "Company"])` |
| Обробник Apply | Змінити повний документ і викликати `ctx.commit_xml(document)` |
| Cancel або закриття вікна без застосування | Викликати `ctx.cancel()` та закрити вікно |
| Режим виконання | `mode=ui` у `adapter.ini` |
| Область змін для рамок | `write_scope=sheet_settings` у `adapter.ini` |
| Обмін XML | `ExpMode=All` та `ImpMode=All` у `settings.xml` |

Цикл подій інтерфейсу має працювати всередині `main()`. Після успішного Apply закрийте вікно й дайте `main()` завершитися. Адаптер перевірить підготовлений XML та запише його у файл обміну; DipTrace імпортує результат після завершення EXE. Виняток після `commit_xml()` відкидає підготовлений результат. Файли, які TitleJob зберігає безпосередньо, наприклад шаблони VPT, автоматично не відкочуються.

[Приклад UI](../examples/ui/plugin.py) демонструє пошук `Designed by` за першим рядком і заміну рядків під ним. Це не повна реалізація TitleJob. Вкладки редактора, таблиця правил, операції із шаблонами та перевірка даних мають залишатися в прикладному коді.

`ctx.environment()` читає успадковані значення середовища процесу та повертає нормалізовані ключі: наприклад, `Company` повертається як `company`. Метод не створює та не редагує змінні проєкту в DipTrace. Зміна `os.environ` усередині плагіна не зберігає ці зміни в проєкті.

Перевірте Apply, Cancel, відсутні змінні та поля з наявним багаторядковим текстом. Переконайтеся, що перший рядок кожного знайденого поля рамки зберігається, а решта даних схеми залишається незмінною.
