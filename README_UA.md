# DipTraceSchPluginAdapter

[English](README.md) · Українська

**Адаптер для створення плагінів DipTrace Schematic на Python.** Він бере на себе запуск плагіна та обмін XML із DipTrace, щоб розробник міг зосередитися на потрібній функції: формуванні документації, перевірці схеми або заповненні рамок.

Не потрібно писати й компілювати окремий EXE для кожного плагіна. Готовий `DipTraceSchPluginAdapter.exe` можна перейменувати; функціональність плагіна реалізується у звичайних Python-файлах. Через API доступні XML-дані, які експортує DipTrace, та вибрані змінні середовища, успадковані від процесу DipTrace.

Версія **0.1.1**, API **1**, ліцензія **MIT**. Незалежний проєкт спільноти.

## Версії та випуски

`build_info.json` у корені репозиторію — джерело версії адаптера та номера API.
Цей випуск має версію **0.1.1**, API **1**. BOMJob **0.2.7** — версія окремого
плагіна, а не попередній випуск адаптера.

Інструмент збірки створює копію метаданих для Python і заголовок для C,
оновлює рядок версії в обох README, вбудовує Windows `FileVersion` і
`ProductVersion` та записує хеш EXE до `build_info.json`.
Не редагуйте згенеровані файли версії та записані хеші вручну.
Встановлений Python-пакет читає свій згенерований `build_info.json`;
нативний EXE містить ту саму версію, вбудовану під час компіляції.

Версію завантаженого або встановленого адаптера можна побачити:

- У назві архіву випуску `DipTraceSchPluginAdapter-0.1.1.zip`.
- У Windows **Властивості → Докладно** для EXE, навіть після перейменування.
- Командою `DipTraceSchPluginAdapter.exe --version`, яка відкриває інформаційне вікно.
- Командою `py -3 python/host.py --version` у репозиторії або
  `py -3 .adapter/host.py --version` у папці встановленого плагіна.
- У полі `adapter_version` файлів `adapter.lock.json`, `context.json` та
  `status.json`, а також у нативному журналі запуску та `worker.log`.
- Через `diptrace_adapter.__version__` і `diptrace_adapter.API_VERSION` у Python.

Версія адаптера та версія плагіна незалежні. Щоб показувати власну версію
плагіна в меню DipTrace, створіть його так:

```powershell
py -3 tools/new_plugin.py D:\PluginBuild\MyPlugin --name MyPlugin --mode job --plugin-version 0.1.1
```

Назва в меню буде **MyPlugin 0.1.1**, а ім’я EXE залишиться `MyPlugin.exe`,
ідентифікатор `plugin_id` — `MyPlugin`. Версію також буде записано до
`[plugin] version` у `adapter.ini`. Без `--plugin-version` назва в меню
залишається без версії. Для наявного плагіна під час випуску оновіть і
`[plugin] version`, і атрибут `Name` у `settings.xml`. Оновлення самого адаптера
не змінює версію плагіна або його назву в меню.
`ctx.adapter_version` та `ctx.plugin_version` повертають ці значення окремо;
`ctx.plugin_version` дорівнює `None`, якщо версію не задано.

Порядок публікації випуску адаптера:

1. Встановіть `version` у кореневому `build_info.json`; оновіть `changes` та
   [CHANGELOG_UA.md](CHANGELOG_UA.md). Змінюйте `api_version` лише за навмисної
   несумісної зміни API разом із відповідними змінами реалізації.
2. Виконайте [збірку та тести](#збірка-самого-адаптера-та-тести), а потім:

   ```powershell
   py -3 tools/versioning.py --check
   py -3 tools/release.py
   ```

   ZIP з’явиться в `build/releases/`. Пакування оновлює обидва файли контрольних
   сум і не включає історію Git, локальні продукти збірки та захоплення.
3. Перегляньте зміни та закомітьте вихідний код, згенеровані метадані, README,
   файли контрольних сум і `dist/DipTraceSchPluginAdapter.exe`. Для цього випуску:

   ```powershell
   git status --short
   git add .
   git commit -m "Release DipTraceSchPluginAdapter 0.1.1"
   git tag -a v0.1.1 -m "DipTraceSchPluginAdapter 0.1.1"
   git push origin main
   git push origin v0.1.1
   ```

4. Створіть GitHub Release із тегу `v0.1.1` і додайте
   `build/releases/DipTraceSchPluginAdapter-0.1.1.zip`.
   Автоматичний архів вихідного коду GitHub не замінює цей іменований файл випуску.
5. У залежних проєктах, наприклад FineBOM, закріпіть повний SHA коміту з команди
   `git rev-parse "v0.1.1^{commit}"` та перескладіть плагін.

Опублікований тег позначає незмінний випуск; для подальших змін використовуйте
нову версію. Тести та пакування самі не надсилають коміти й не публікують
GitHub Releases.

## Що входить до адаптера

- **EXE для Windows x64** — приймає від DipTrace шлях до XML та запускає Python без вікна консолі.
- **Службові Python-модулі** — зберігають копію XML, запускають код плагіна, ведуть діагностику та повертають дозволені зміни.
- **API `main(ctx)`** — точка входу для власного плагіна.
- **Генератор структури плагіна**, приклади, тести та інструмент оновлення залежності.

Правила BOM, робота з OTS/VPT та інші прикладні функції реалізуються в кінцевих плагінах. API 1 має Python-точку входу; окремого API для інших мов у цій версії немає.

Python не вбудований в EXE. На комп’ютері користувача потрібен **Python 3.11 або новіший**. Для прикладу з вікном потрібен також Tkinter. Git потрібен розробнику для отримання репозиторію та роботи з інструментами залежності; користувачеві готового плагіна Git не потрібен.

Поточний засіб запуску призначений для **Windows x64**. На Linux можна підготувати папку плагіна, тестувати Python-код і зібрати Windows EXE. Підтримку запуску цього адаптера в macOS не реалізовано й не перевірено.

## Два режими роботи

| Режим | Що відбувається | Повернення змін у схему |
| --- | --- | --- |
| `job` | Адаптер копіює XML, запускає фоновий процес і звільняє DipTrace. Python завершується після виконання завдання. | Заборонено; у `settings.xml` потрібен `ImpMode=None`. |
| `ui` | Адаптер чекає завершення Python-коду, зокрема закриття вікна. Потім повертає підготовлений результат. | Лише після явного `ctx.commit_xml()` та успішного завершення `main()`. |

Для генерації звітів обирайте `job`, для редактора з кнопками **Apply/Cancel** — `ui`. Режим визначає життєвий цикл та можливість імпорту; конкретна бібліотека інтерфейсу не має значення.

Під час роботи `ui` DipTrace очікує завершення плагіна. Це обмін файлами за один запуск, а не постійне з’єднання з активною схемою. Закриття вікна без підготовленого результату залишає схему без змін.

## Швидкий старт: створити та запустити приклад

Наведені нижче команди виконуються у **PowerShell на Windows**. Шлях `D:\PluginBuild` можна замінити на власний робочий каталог.

### 1. Отримайте репозиторій

```powershell
git clone https://github.com/steppefort/DipTraceSchPluginAdapter.git
cd DipTraceSchPluginAdapter
py -3 --version
git --version
```

Переконайтеся, що Python має версію 3.11 або новішу. Для прикладу з UI перевірте Tkinter:

```powershell
py -3 -m tkinter
```

Має відкритися тестове вікно Tkinter; після перевірки закрийте його.

### 2. Створіть папку плагіна

Для автоматичного завдання:

```powershell
py -3 tools/new_plugin.py D:\PluginBuild\DemoJob --name DemoJob --mode job
```

Для прикладу з вікном:

```powershell
py -3 tools/new_plugin.py D:\PluginBuild\DemoUI --name DemoUI --mode ui
```

Це дві незалежні команди: достатньо виконати одну для потрібного режиму. Каталог призначення **ще не повинен існувати**. Якщо він уже є, скрипт завершиться помилкою, щоб не перезаписати файли.

`tools/new_plugin.py` виконує такі дії:

1. Створює каталог призначення та копіює до нього `examples/job/plugin.py` або `examples/ui/plugin.py`.
2. Створює `adapter.ini` з вибраним режимом і назвою плагіна.
3. Створює `settings.xml`: `ExpMode=All`, а `ImpMode=None` для `job` або `ImpMode=All` для `ui`.
4. Копіює готовий `dist/DipTraceSchPluginAdapter.exe`, перейменовуючи його відповідно до `--name`.
5. Копіює службові Python-модулі та ліцензійні повідомлення до `.adapter`.
6. Записує `adapter.lock.json` із версією API, ідентифікатором коміту та SHA-256 скопійованих файлів.

**Результат — папка плагіна, готова до встановлення, з демонстраційною функціональністю.** Скрипт виводить її шлях. Він не компілює ваш Python-код, не встановлює Python і не запускає DipTrace. Повторна збірка EXE для цього кроку не потрібна.

Для `DemoUI` будуть створені такі основні файли:

| Шлях у папці плагіна | Призначення |
| --- | --- |
| `DemoUI.exe` | Перейменований готовий адаптер. |
| `plugin.py` | Код прикладу; саме тут починається розробка власного плагіна. |
| `adapter.ini` | Режим, Python, точка входу та дозволена область змін. |
| `settings.xml` | Назва плагіна в DipTrace, EXE та параметри експорту/імпорту. |
| `adapter.lock.json` | Відомості про встановлену залежність та хеші файлів. |
| `.adapter/host.py` | Службова точка входу Python. |
| `.adapter/diptrace_adapter/` | Реалізація API та обміну XML. |

Назва з `--name` використовується для EXE, `plugin_id` і початкової назви в меню DipTrace. Дозволено 1–80 символів: латинські літери, цифри, `_`, `-`, `.`; перший символ — літера або цифра.

### 3. Налаштуйте Python

У створеному `adapter.ini` за замовчуванням зазначено:

```ini
[python]
executable = pyw.exe
```

Якщо цей засіб запуску недоступний або потрібно вибрати конкретний інтерпретатор, вкажіть абсолютний шлях до свого `pythonw.exe`, наприклад:

```ini
[python]
executable = C:\Python312\pythonw.exe
```

Це приклад шляху: замініть його на фактичне розташування Python. Шлях записується **без лапок**, навіть якщо містить пробіли. Вирази на кшталт `%LOCALAPPDATA%` у цьому параметрі не розгортаються. Адаптер додає `-3` лише для `py.exe` або `pyw.exe`; додаткові аргументи в `executable` не підтримуються.

### 4. Встановіть плагін у DipTrace

1. Скопіюйте **всю** папку `DemoJob` або `DemoUI`, включно з `.adapter`, до `Plugins\Schematic` у каталозі встановлення DipTrace. Типовий шлях: `C:\Program Files\DipTrace\Plugins\Schematic\DemoUI`.
2. Залиште один EXE у корені папки плагіна. Кожен плагін має власну папку.
3. Перезапустіть **Schematic Capture**, відкрийте схему та виберіть плагін у **Tools > Plugins**.

Генератор не виконує встановлення автоматично. Копіювання до `Program Files` може потребувати прав адміністратора.

### 5. Перевірте результат

- **DemoJob:** вікно не відкривається. Приклад читає XML та змінні `projectname` і `revision`, після чого записує `summary.json` до каталогу діагностики запуску. Схему він не змінює. Завершення перевіряється за `status.json` зі значенням `ok`.
- **DemoUI:** відкривається вікно з полем автора. Початкове значення береться зі змінної `author`, якщо вона доступна. Кнопка **Apply to active project** шукає текстові поля рамок із першим рядком `Designed by`, зберігає цей рядок й замінює всі наступні введеним значенням. Для перевірки у схемі має бути таке поле. **Cancel** закриває вікно без змін.

Діагностика міститься в `%LOCALAPPDATA%\DipTraceSchPluginAdapter\<plugin_id>\captures`. Файл `latest.json` у цьому каталозі вказує на папку останнього запуску.

## Як написати власний плагін

### 1. Створіть основу з потрібною назвою

З кореня репозиторію виконайте:

```powershell
py -3 tools/new_plugin.py D:\PluginBuild\ProjectInfo --name ProjectInfo --mode job
```

Надалі працюйте у **`D:\PluginBuild\ProjectInfo`**. Змінюйте її `plugin.py`; файли `examples` у репозиторії адаптера змінювати не потрібно. Не запускайте генератор повторно для цієї самої папки.

### 2. Замініть демонстраційний код своїм

Наприклад, цей повний вміст `plugin.py` створює файл `Docs\project-info.json` у папці проєкту:

```python
import json


def main(ctx):
    project_dir = ctx.project_dir
    if project_dir is None:
        raise ValueError("DipTrace не передав шлях до проєкту")
    if not project_dir.is_dir():
        raise ValueError(f"Каталог проєкту не існує: {project_dir}")

    variables = ctx.environment(["projectname", "revision", "Company"])
    output_dir = project_dir / "Docs"
    output_dir.mkdir(parents=True, exist_ok=True)
    output_path = output_dir / "project-info.json"

    data = {
        "projectname": variables.get("projectname", ""),
        "revision": variables.get("revision", ""),
        "company": variables.get("company", ""),
    }
    output_path.write_text(
        json.dumps(data, ensure_ascii=False, indent=2) + "\n",
        encoding="utf-8",
    )
    ctx.log(f"Створено {output_path}")
```

Адаптер сам викликає `main(ctx)` і передає контекст поточного запуску. Створювати `ctx` вручну чи додавати виклик `main()` внизу файлу не потрібно. Простий запуск `python plugin.py` лише завантажить визначення функції й не виконає завдання.

У прикладі відсутні змінні записуються порожніми рядками, а повторний запуск **перезаписує** `project-info.json`. За потреби додайте власну перевірку обов’язкових значень або правило іменування файлів.

`ctx.environment()` повертає нормалізовані ключі: для `Company` потрібно читати `variables["company"]`. XML схеми можна отримати через `ctx.document()` і обробляти стандартним `xml.etree.ElementTree`.

### 3. Додайте свої модулі та ресурси

Розміщуйте допоміжні `.py`, шаблони та налаштування поруч із `plugin.py` або в підкаталогах. Для шляхів використовуйте `ctx.plugin_dir`, `ctx.project_dir` та `ctx.run_dir`, а не припущення про поточний каталог процесу.

Зовнішні Python-пакети встановлюються окремо **в інтерпретатор, указаний у `adapter.ini`**. Адаптер не встановлює залежності під час запуску. Для публікації такого плагіна додайте `requirements.txt` та інструкцію встановлення.

У `settings.xml` можна змінити атрибути `Name` і `Hint` елемента `Source` — назву та підказку для користувача. `ExeFile` має відповідати імені EXE. Зберігайте узгодженість `mode` в INI та `ExpMode`/`ImpMode` в XML.

### 4. Запустіть власний код

Скопіюйте папку `ProjectInfo` до DipTrace так само, як у швидкому старті, й запустіть плагін зі збереженого проєкту. Перевірте `Docs\project-info.json` та діагностику.

Під час подальшої розробки оновлюйте файли **в установленій копії плагіна** перед наступним запуском. Редагування лише `D:\PluginBuild\ProjectInfo\plugin.py` не змінює вже скопійований файл у `Plugins\Schematic`.

### 5. Якщо потрібне редагування схеми та UI

Створіть основу з `--mode ui` і використайте згенерований `plugin.py` як приклад обробників **Apply/Cancel**:

1. На початку `main(ctx)` прочитайте `document = ctx.document()`.
2. Побудуйте інтерфейс і запустіть його цикл подій усередині `main()`.
3. В обробнику **Apply** перевірте введені дані та внесіть зміни до `document`.
4. Викличте `ctx.commit_xml(document)`. Якщо виклик успішний, закрийте вікно, щоб `main()` завершилася.
5. В обробнику **Cancel** викличте `ctx.cancel()` та закрийте вікно.

`commit_xml()` готує результат. Імпорт у DipTrace відбудеться після успішного завершення `main()` і виходу адаптера. Сам виклик `commit_xml()` не оновлює відкриту схему негайно.

За замовчуванням `write_scope = sheet_settings` дозволяє змінювати лише `/Source/Schematic/SheetSettings`, зокрема рамки. Для редагування компонентів або інших частин XML потрібне `write_scope = full`. Повертайте **повний документ**, зберігаючи вузли та атрибути, яких ваша функція не стосується.

### 6. Підготуйте плагін до поширення

До пакета кінцевого плагіна входять його EXE, `.adapter`, `adapter.ini`, `settings.xml`, `adapter.lock.json`, ваш Python-код і потрібні ресурси. Вихідний C-код адаптера, його тести й інструменти збірки до встановленого плагіна копіювати не потрібно. Збережіть ліцензійні повідомлення, які копіює генератор.

Вкажіть у документації плагіна вимоги до Python, додаткові залежності, порядок встановлення та очікуваний результат запуску. Для відтворюваного випуску закріпіть коміт адаптера, як описано нижче.

## Налаштування `adapter.ini`

Приклад для UI-плагіна:

```ini
[adapter]
api_version = 1
plugin_id = DemoUI
mode = ui
write_scope = sheet_settings
capture_dir =

[python]
executable = pyw.exe

[plugin]
entry = plugin.py
```

| Параметр | Значення |
| --- | --- |
| `api_version` | Для цього випуску — `1`. |
| `plugin_id` | Ідентифікатор плагіна, зокрема для окремого каталогу діагностики. |
| `mode` | `job` або `ui`. |
| `write_scope` | `sheet_settings` або `full`; повернення змін доступне лише в `ui`. |
| `capture_dir` | Порожнє значення означає типовий каталог діагностики. Відносний шлях відраховується від папки плагіна. |
| `executable` | `pyw.exe` або абсолютний шлях до потрібного Python. |
| `entry` | Шлях до Python-файлу з `main(ctx)`; відносний шлях відраховується від папки плагіна. |

INI підтримує UTF-8 із BOM або без нього та UTF-16LE з BOM. Коментарі записуйте окремими рядками.

## API плагіна

| Виклик або властивість | Призначення |
| --- | --- |
| `ctx.exchange_path` | Шлях до збереженої копії XML. Цей файл не можна змінювати. |
| `ctx.read_xml()` | Початкові байти XML із перевіркою хешу. |
| `ctx.document()` | Нове дерево `ElementTree` з XML; зберігає коментарі та невідомі вузли. |
| `ctx.project_dir` | `Path` із `ProjectDir` у XML або `None`. |
| `ctx.plugin_dir` | Каталог установленого плагіна. |
| `ctx.run_dir` | Каталог діагностики конкретного запуску. |
| `ctx.plugin_id`, `ctx.mode` | Ідентифікатор та режим цього запуску. |
| `ctx.environment(names)` | Словник запитаних успадкованих змінних; ключі нормалізуються без урахування регістру. Відсутніх змінних у словнику немає. |
| `ctx.commit_xml(bytes_or_root)` | Підготувати повний XML для повернення; лише `ui`. |
| `ctx.cancel()` | Відкинути підготовлений результат. |
| `ctx.log(message)` | Додати повідомлення до `plugin.log`. |

`main()` повертає `None` або `0`. Виняток чи ненульовий результат скасовує підготовлений XML. Повернення без `commit_xml()` також залишає схему без змін. Це правило стосується обміну зі схемою; файли, які створив сам плагін, автоматично не відкочуються.

API 1 для `ui` вимагає `ExpMode=All` та `ImpMode=All`. Часткове повернення окремих об’єктів не підтримується. Докладніше: [API та життєвий цикл](docs/API.md).

### Змінні середовища

`ctx.environment(["author", "Company"])` читає вибрані значення з **оточення дочірнього процесу**, успадкованого під час запуску. Це не читання постійних системних налаштувань Windows. Імена можна передавати без обгортки або у вигляді `<author>` чи `%author%`.

Метод **не створює та не редагує** змінні в **Tools > Environment variables** DipTrace. Знімок `selected_environment.json` містить лише запитані знайдені значення; під час ручного повторного запуску API не підставляє їх автоматично замість поточного оточення.

## Залежність від репозиторію адаптера

Код кінцевого плагіна можна вести в окремому репозиторії. Зв’язок з адаптером фіксується через конкретний коміт та `adapter.lock.json`; завантажувати адаптер під час кожного запуску плагіна не потрібно.

`new_plugin.py` створює **новий** плагін із поточної локальної копії адаптера. `vendor_adapter.py` встановлює або оновлює **лише залежність** у вже підготовленій папці плагіна.

З кореня клонованого репозиторію адаптера, для вже створеного `ProjectInfo`:

```powershell
$adapterCommit = (git rev-parse HEAD).Trim()
py -3 tools/vendor_adapter.py --repo https://github.com/steppefort/DipTraceSchPluginAdapter.git --commit $adapterCommit --dest D:\PluginBuild\ProjectInfo --exe ProjectInfo.exe
```

Обраний коміт має бути доступний у вказаному репозиторії та містити `dist/DipTraceSchPluginAdapter.exe`. Для оновлення виберіть перевірений коміт потрібного випуску й передайте його повний 40-символьний SHA у `--commit`; назву рухомої гілки на кшталт `main` інструмент не приймає.

Інструмент отримує саме цей коміт, перевіряє його SHA, копіює EXE та Python-модулі й оновлює `adapter.lock.json`. Ваші `plugin.py`, INI, `settings.xml` та шаблони він не змінює. Вкажіть поточне ім’я EXE плагіна, щоб воно залишилося узгодженим із `settings.xml`.

Перед оновленням установленої копії завершіть запущені процеси плагіна: скрипт сам їх не зупиняє. Попередні службові модулі зберігаються в `.adapter.previous`; це не повна резервна копія плагіна.

Залежність також можна тримати як Git-підмодуль і запускати її інструменти під час підготовки випуску. Поширюйте готову папку плагіна зі службовими модулями, щоб установленому плагіну не були потрібні Git або мережеве підключення.

## Відлагодження без запуску EXE

Python-частину можна запустити вручну з копією XML, отриманою від DipTrace. Наприклад, для `ProjectInfo`:

```powershell
py -3 D:\PluginBuild\ProjectInfo\.adapter\host.py --config D:\PluginBuild\ProjectInfo\adapter.ini --exchange D:\PluginBuild\exchange-test.xml
```

Спочатку створіть `exchange-test.xml` як **копію** XML потрібного захоплення. Для `ui` цей файл може бути замінений результатом. Такий запуск перевіряє Python-код та обмін файлами, але не оновлює відкриту схему DipTrace і не перевіряє нативний EXE.

Змінні проєкту не з’являються в ручному запуску автоматично. Для тесту задайте потрібні значення в поточній сесії PowerShell перед командою запуску:

```powershell
$env:projectname = 'ExampleProject'
$env:revision = '1'
$env:Company = 'Example Company'
```

У режимі `job` команда може повернути керування раніше, ніж завершиться завдання. Перевірте `status.json` у новому каталозі захоплення. Для UI потрібне графічне середовище та відповідна бібліотека інтерфейсу.

## Збірка самого адаптера та тести

Цей крок потрібен, якщо ви змінюєте `native/launcher.c` або хочете самостійно зібрати EXE. Для написання звичайного Python-плагіна використовуйте готовий файл із `dist`.

З кореня репозиторію у PowerShell:

```powershell
py -3 -m pip install ziglang==0.14.1
$adapterZig = (py -3 -c "import pathlib, ziglang; print(pathlib.Path(ziglang.__file__).parent / 'zig.exe')").Trim()
py -3 tools/build.py --zig $adapterZig
py -3 -m unittest discover -s tests -v
```

На Linux можна крос-компілювати той самий Windows x64 EXE:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install ziglang==0.14.1
adapter_zig="$(python -c 'import pathlib, ziglang; print(pathlib.Path(ziglang.__file__).parent / "zig")')"
python tools/build.py --zig "$adapter_zig"
python -m unittest discover -s tests -v
```

Результат збірки — **`dist/DipTraceSchPluginAdapter.exe`**. Скрипт перевіряє формат PE x64 та графічну підсистему Windows. Збірка не оновлює вже створені папки кінцевих плагінів автоматично.

Для створення папки плагіна на Linux використовуйте, наприклад, `python tools/new_plugin.py ./build/MyPlugin --name MyPlugin --mode job`. Результат також призначений для встановлення у Windows.

У репозиторії є GitHub Actions workflow для збірки й тестів на Linux та Windows. Тест нативного запуску виконується лише у Windows. Ці перевірки не замінюють перевірку встановленого плагіна безпосередньо в DipTrace.

## Підключення наявного плагіна

Основний порядок міграції:

1. Створіть нову папку через `new_plugin.py` у відповідному режимі.
2. Перенесіть прикладний Python-код, шаблони й налаштування наявного плагіна.
3. Реалізуйте `main(ctx)` і замініть читання початкового XML на `ctx.read_xml()` або `ctx.document()`.
4. Для редактора передавайте повний змінений XML через `ctx.commit_xml()` після підтвердження користувачем.
5. Перевірте результат у DipTrace та запакуйте всю папку.

[Міст BOMJob](examples/bomjob_bridge/plugin.py) показує виклик наявного обробника BOMJob 0.2.7: розмістіть міст як `plugin.py` поруч із модулями BOMJob, збережіть `bomjob.ini` та шаблони, використовуйте `mode=job` і `ImpMode=None`.

[Приклад UI](examples/ui/plugin.py) демонструє редагування поля рамки. Повний редактор шаблонів або змінних середовища потрібно реалізувати окремо. Додаткові рекомендації: [нотатки щодо міграції](docs/MIGRATION_UA.md).

## Діагностика

Кожен запуск має окремий підкаталог у `%LOCALAPPDATA%\DipTraceSchPluginAdapter\<plugin_id>\captures`, якщо `capture_dir` не перевизначено.

| Файл | Призначення |
| --- | --- |
| `context.json` | Параметри конкретного запуску. |
| `exchange.xml` | Незмінна початкова копія XML. |
| `status.json` | Стан виконання: `starting`, `ok`, `changed`, `cancelled` або `error`. |
| `worker.log` | Стандартний вивід і потік помилок Python-процесу. |
| `plugin.log` | Повідомлення `ctx.log()` та помилки виконання, якщо вони були. |
| `selected_environment.json` | Знайдені змінні, явно запитані через API. |
| `result.xml` | Підготовлений змінений XML, якщо був `commit_xml()`. |
| `applied.json` | Підтвердження запису результату в обмінний файл. |

Не всі файли створюються в кожному запуску. `changed` означає підготовлений результат; запис у вихідний обмінний файл додатково фіксується в `applied.json`. Для помилок початкового запуску перевірте також `%LOCALAPPDATA%\DipTraceSchPluginAdapter\last_error.log`.

Автоматичне очищення захоплень не реалізовано. Вони можуть містити дані проєкту та вибрані значення змінних. API перевіряє область змін XML, але не є пісочницею: Python-код плагіна працює з правами користувача.
